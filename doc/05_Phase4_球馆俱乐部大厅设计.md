## 一、业务定位

### 1.1 本阶段要解决的问题

论坛系统已经具备发帖、评论、点赞等基础社交能力，但还没有真正支撑“约球成局”的业务闭环。

本阶段新增“球馆 -> 俱乐部 -> 活动大厅”的组织链路，目标是让用户可以：

1. 进入 App 后先看到附近球馆
2. 进入某个球馆后看到该球馆下的俱乐部列表
3. 进入某个俱乐部的活动大厅后，直观看到：
   - 当前在线人数
   - 各个场地的报名情况
   - 每个坑位是谁，占坑状态如何
   - 哪些人还在观望
   - 大厅内聊天消息
   - 俱乐部广播消息
4. 用户占坑后，再手动确认参加
5. 某个场地满足条件后形成“成局”状态
6. 球馆老板根据哪个俱乐部先锁定场地，优先把场地给哪个俱乐部

### 1.2 与现有“闪动/活动制”模式的区别

本方案不是单纯复制外部活动平台，而是结合当前产品阶段，采用更适合单人主导和后续扩展的模式：

1. 球馆由系统预录入，首期由产品方维护
2. 球馆下允许存在多个俱乐部
3. 活动既可以由俱乐部发起，也可以由个人发起
4. 用户进入大厅时，更强调“在线氛围”和“即时组局感”
5. 广播能力由俱乐部使用，用于吸引用户补位

## 三、核心流程

### 3.1 用户主流程

1. 用户打开 App
2. 在底部第一个 Tab 进入球馆列表
3. 看到“晴天羽毛球馆”
4. 点击进入该球馆
5. 进入俱乐部列表，例如：
   - 俱乐部 A
   - 俱乐部 B
   - 俱乐部 C
6. 点击俱乐部进入活动大厅
7. 在大厅内可以：
   - 查看当前在线人数
   - 查看 10 个场地的状态
   - 查看每个场地 6 个坑位当前是谁
   - 进入观望状态
   - 占坑
   - 取消占坑
   - 确认参加
   - 发送大厅消息
8. 当某个场地 6 个坑位都有人且全部确认时，场地变成“已成局/已锁定”
9. 球馆老板根据锁定顺序，把真实场地资源优先给先锁定的俱乐部
10. 若球馆剩余场地不足，后面的俱乐部会出现“无场地可定”的真实情况

### 3.2 球馆老板视角的业务含义

对于球馆老板来说，某个俱乐部大厅中的“成局”并不等于系统自动完成订场，而是表示：

1. 该俱乐部已经在某个场地组织好了 6 个人
2. 该场地具备优先申请真实球场的资格
3. 球馆老板可根据成局先后顺序决定实际给哪个俱乐部哪块场地

因此在数据层面，系统需要区分：

- 大厅里的“虚拟场地位”
- 球馆老板最终分配的“真实场地资源”

本阶段先实现“虚拟场地位 + 成局状态”，真实订场确认可在后续 Phase 5 或 Phase 6 扩展。

## 五、活动大厅设计

### 5.1 顶部信息区

至少展示：

- 球馆名称：晴天羽毛球馆
- 俱乐部名称：俱乐部 A / B / C
- 时间段：今晚 19:30 - 22:00
- 在线人数：例如“在线 23 人”

### 5.2 广播区

展示形式建议：

1. 顶部橙色跑马灯
2. 或悬浮通知条

广播内容由俱乐部发送，例如：

- 1号场高质量缺人，L4 以上速来
- 2号场差一位，双打局

规则：

1. 普通用户只能在大厅聊天区发言
2. 只有俱乐部具备广播权限
3. 广播有次数消耗字段，后端需要预留
4. 当前阶段前端只需完成展示和基础发送，不做购买次数体系

### 5.3 场地区

晴天羽毛球馆固定 10 个场地。

每个场地固定 6 个坑位，采用 2 行 x 3 列或 3 行 x 2 列布局展示。

每个场地卡片建议展示：

- 场地编号，例如“1号场”
- 参与人数进度，例如“3/6 已确认”
- 等级要求，例如“L3+”
- 模式，例如“双打”
- 当前状态，例如：
  - 观望中
  - 招募中
  - 待确认
  - 已成局

#### 坑位状态

一个坑位有 4 种状态：

1. 空位
2. 已占坑未确认
3. 已确认
4. 已锁定场地中的已确认位

#### 坑位展示元素

若该坑位有人，需要显示：

- 头像
- 昵称
- 等级

#### 交互规则

1. 用户未占坑时，点击空位可占坑
2. 一个用户在同一活动中只能占一个坑
3. 用户占坑后，可以取消占坑
4. 用户占坑后，需要再次点击“确认参加”
5. 当同一场地 6 人全部确认时，该场地进入“已成局”状态
6. 成局后场地卡片视觉高亮，禁止继续抢占

### 5.4 观望区

观望区用于展示已进入大厅但尚未占坑的用户。

展示内容：

- 头像
- 昵称
- 等级

意义：

1. 让大厅看起来更有氛围
2. 让用户能看到熟人是否在线
3. 支撑“你快来 1 号场补位”这样的即时互动场景

### 5.5 聊天区

大厅内置轻量聊天区，不做完整 IM。

规则：

1. 所有人可发言
2. 每个用户 60 秒最多发送 1 条消息
3. 消息只保留当天，当天结束后清理
4. 聊天区显示最近若干条消息即可，例如最近 20 条

消息格式建议：

- 张三 L4：1号场差一个人，来不？
- 李四 L3：我可以

## 六、客户端数据模型设计

### 6.1 核心对象关系

```text
Venue 球馆
  -> Club 俱乐部
      -> Activity 活动
          -> ActivitySlot 坑位
          -> ActivityPresence 在线心跳
          -> ActivityMessage 聊天消息

Club -> Broadcast 广播
```

### 6.2 表设计

#### venue

用途：球馆基础信息。

核心字段建议：

- id
- name
- city
- address
- latitude
- longitude
- court_count
- status
- created_at
- updated_at

当前初始化数据：

- 晴天羽毛球馆
- court_count = 10

#### club

用途：球馆下的俱乐部。

核心字段建议：

- id
- venue_id
- name
- creator_id
- description
- status
- broadcast_credits
- created_at
- updated_at

状态建议：

- pending：待审核
- active：可用
- frozen：冻结
- deleted：删除

当前测试数据：

- 俱乐部 A
- 俱乐部 B
- 俱乐部 C

#### activity

用途：某俱乐部或个人发起的一次活动大厅。

核心字段建议：

- id
- venue_id
- club_id，可为空，表示个人发起
- creator_id
- title
- activity_date
- time_slot
- level_requirement
- match_type
- court_count
- max_per_court
- status
- created_at
- updated_at

建议值：

- time_slot：EVENING
- match_type：DOUBLES
- max_per_court：6

状态建议：

- open：开放中
- locked：已有成局/锁定
- finished：结束
- canceled：取消

#### activity_slot

用途：某个活动大厅中每个场地每个坑位的占位情况。

核心字段建议：

- id
- activity_id
- court_number
- slot_number
- user_id
- slot_status
- created_at
- updated_at

slot_status：

- reserved：已占坑
- confirmed：已确认
- locked：所属场地已成局

约束建议：

1. `(activity_id, court_number, slot_number)` 唯一
2. `(activity_id, user_id)` 唯一，保证一个用户只能占一个坑

#### activity_presence

用途：标记哪些用户当前在线进入了大厅。

核心字段建议：

- id
- activity_id
- user_id
- last_ping_at
- created_at

逻辑：

- 用户进入大厅时插入或更新
- 前端轮询期间同步 ping
- 超过 30 秒未 ping 的用户视为离线

#### activity_message

用途：大厅聊天消息。

核心字段建议：

- id
- activity_id
- user_id
- content
- created_at

#### broadcast

用途：俱乐部广播。

核心字段建议：

- id
- club_id
- sender_id
- content
- expires_at
- created_at

## 八、状态与规则

### 8.1 用户在大厅中的状态

1. 观望中：进入大厅但未占坑
2. 已占坑：占到某个场地某个位置
3. 已确认：占坑后确认参加
4. 已离开：退出大厅或超时无心跳

### 8.2 场地状态

1. open：开放中
2. recruiting：招募中
3. waiting_confirm：人数已到但有人未确认
4. locked：6 人都确认，已成局

### 8.3 约束规则

1. 一个用户在同一活动中最多占一个坑
2. 普通用户不可发全局广播
3. 聊天消息 60 秒限频
4. 超过 30 秒无 ping 视为掉线
5. 掉线后若已占坑，服务端可选择自动释放或先保留短暂时间

MVP 建议：

- 掉线后先保留坑位 3 分钟，再由清理任务释放

## 十四、结论

Phase 4 的目标不是简单再加一个列表页，而是正式进入“打球组织”业务。

这套系统的核心体验在于：

1. 看得到人
2. 看得到场地
3. 看得到谁在观望、谁已经确认
4. 有俱乐部广播氛围
5. 最终形成可落地的成局结果

客户端开发要重点保证大厅页面的状态可视化。
